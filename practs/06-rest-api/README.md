# Практична робота №6. Проєктування та розробка REST API

> ⚠️ **WIP** — матеріал ще в розробці, зміст може змінюватись.

**Модуль:** 2 — мікропроєкт, крок 2 з 4
**Тип застосунку:** розширення проєкту з ПР №5 (той самий домен/репозиторій)
**Обсяг:** 2–3 год аудиторних + СРС

> Використовується той самий варіант домену, що й у ПР №5 (див. таблицю варіантів у файлі ПР №5).

## Мета роботи

Навчитися проєктувати та реалізовувати REST API відповідно до принципів REST: коректне використання HTTP-методів і кодів статусу, DTO та валідація вхідних даних, робота з пов'язаними сутностями, фільтрація/сортування/пагінація колекцій.

## Завдання

- Розширити модель даних із ПР №5: додати щонайменше третю пов'язану сутність або зв'язок «багато-до-багатьох» (за потреби домену).
- Ввести DTO-класи (Request/Response) для кожної сутності API — контролери не повинні повертати EF-моделі напряму; налаштувати мапінг (вручну або через AutoMapper).
- Реалізувати серверну валідацію вхідних DTO (Data Annotations та/або FluentValidation), повертати 400 Bad Request з деталями помилок при невалідних даних.
- Реалізувати коректну обробку відсутніх ресурсів (404 Not Found) та інших помилкових ситуацій, використовуючи відповідні коди статусу (200, 201, 204, 400, 404) і заголовок Location при POST.
- Реалізувати для колекційного ендпоінта підтримку пагінації (page/pageSize), фільтрації за щонайменше одним полем та сортування за щонайменше одним полем через query-параметри.
- Реалізувати ендпоінт(и) для роботи з пов'язаними сутностями (наприклад, отримання всіх книг певного автора, або вкладене створення).
- Підключити та налаштувати OpenAPI (Microsoft.AspNetCore.OpenApi) + Scalar UI з описом моделей та прикладами (XML-коментарі або анотації).
- Реалізувати глобальну обробку помилок (middleware/ExceptionFilter) для уніфікованого формату відповіді про помилку (наприклад, ProblemDetails).

## Теоретичні відомості (стисло)

Принципи REST (ресурси, uniform interface, stateless), відповідність HTTP-методів CRUD-операціям, коди стану HTTP, підхід DTO та причини не використовувати EF-моделі як контракт API, валідація вхідних даних, пагінація/фільтрація/сортування колекцій, middleware та централізована обробка виключень, стандарт ProblemDetails (RFC 7807).

## Порядок виконання

1. Розширити модель даних та застосувати нову міграцію.
2. Ввести DTO та мапінг моделі ⇄ DTO для всіх сутностей API.
3. Додати валідацію вхідних DTO та перевірити реакцію API на некоректні дані.
4. Реалізувати пагінацію/фільтрацію/сортування для колекційного ендпоінта.
5. Реалізувати роботу з пов'язаними сутностями через окремі ендпоінти.
6. Підключити централізовану обробку помилок у форматі ProblemDetails.
7. Оновити документацію Scalar UI, протестувати всі сценарії через Postman/Scalar (позитивні та негативні).
