# Практична робота №8. Архітектурні патерни та тестування .NET-застосунку

**Модуль:** 2 — мікропроєкт, крок 4 з 4 (фінальний)
**Тип застосунку:** рефакторинг та тестування проєкту з ПР №5–7 (той самий домен/репозиторій)
**Обсяг:** 2–3 год аудиторних + СРС

> Використовується той самий варіант домену, що й у ПР №5–7 (див. таблицю варіантів у файлі ПР №5) — фінальна, архітектурно оформлена та протестована версія мікропроєкту.

## Мета роботи

Навчитися застосовувати архітектурні патерни (Repository, Unit of Work, елементи Clean Architecture) для розшарування логіки застосунку та писати модульні (unit) й інтеграційні (integration) тести для .NET Web API.

## Завдання

- Виконати рефакторинг проєкту: винести звернення до DbContext у шар репозиторіїв (Repository pattern) з інтерфейсами (IRepository<T> або спеціалізовані інтерфейси на кожну сутність).
- Реалізувати Unit of Work (IUnitOfWork) для узгодженого збереження змін кількох репозиторіїв в одній транзакції.
- Винести бізнес-логіку з контролерів у окремий сервісний шар (Service/Application layer); контролери мають лише приймати запити, викликати сервіси та формувати HTTP-відповідь.
- Організувати проєкт у кілька шарів/проєктів рішення (наприклад, *.Api, *.Application, *.Domain, *.Infrastructure) або, як мінімум, у чітко розділені папки з однонапрямленими залежностями (демонстрація принципів Clean Architecture в обсязі, доступному студенту).
- Написати unit-тести (xUnit + Moq — галузевий стандарт для мокування в .NET) для сервісного шару: щонайменше 6 тестів, що покривають позитивні та негативні сценарії (валідні дані, відсутній ресурс, порушення бізнес-правила), з ізоляцією через мокування репозиторіїв.
- За бажання (як розширення завдання) — реалізувати частину операцій запису через патерн CQRS з використанням бібліотеки MediatR (окремі Command/Query та їх обробники) замість або на додаток до звичайного сервісного шару; це також покриває тему «Архітектурні патерни: CQRS» з лекційного курсу.
- Написати інтеграційні тести API (WebApplicationFactory<Program> + окрема тестова SQLite-база, наприклад in-memory SQLite-з'єднання) для щонайменше 3 ендпоінтів, що перевіряють реальні HTTP-відповіді та коди статусу.
- Налаштувати запуск усіх тестів однією командою (dotnet test) та переконатися, що всі тести проходять успішно.

## Теоретичні відомості (стисло)

Патерн Repository та його призначення для абстрагування джерела даних, патерн Unit of Work, шарова архітектура та принципи Clean Architecture (незалежність домену від інфраструктури, напрямок залежностей), патерн CQRS та бібліотека MediatR як типова реалізація для .NET (розділення Command/Query, pipeline-behaviors), відмінність unit-тестів від інтеграційних, мокування залежностей (Moq), WebApplicationFactory для тестування ASP.NET Core API «з середини», структура тесту AAA (Arrange-Act-Assert).

## Порядок виконання

1. Спроєктувати інтерфейси репозиторіїв та Unit of Work, реалізувати їх на основі EF Core.
2. Перенести бізнес-логіку з контролерів у сервісний шар, що працює через інтерфейси репозиторіїв/UoW (Dependency Injection).
3. Реорганізувати структуру рішення на логічні шари/папки, перевірити відсутність порушення напрямку залежностей.
4. Створити тестовий проєкт, написати unit-тести сервісного шару з мокуванням залежностей.
5. Написати інтеграційні тести ключових ендпоінтів API з ізольованою тестовою базою даних.
6. Запустити dotnet test, переконатися у проходженні всіх тестів, за потреби виміряти покриття коду.

- висновки (2–4 речення) щодо отриманих результатів та труднощів виконання.

## Контрольні питання

1. Яку проблему вирішує патерн Repository і чому це полегшує тестування бізнес-логіки?
2. У чому призначення Unit of Work і чим він відрізняється від окремих незалежних репозиторіїв?
3. Чим unit-тест принципово відрізняється від інтеграційного тесту? Наведіть приклад кожного для цього проєкту.
4. Навіщо в unit-тестах сервісного шару мокати репозиторії, а не використовувати реальну базу даних?
5. Який основний принцип Clean Architecture визначає напрямок залежностей між шарами (Domain, Application, Infrastructure, Api)?
6. Як WebApplicationFactory дозволяє тестувати Web API «end-to-end» без розгортання окремого сервера?
