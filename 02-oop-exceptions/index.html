    Практична робота №2. ООП та обробка виключень у консольному застосунку¶

    ⚠️ WIP — матеріал ще в розробці, зміст може змінюватись.

    Модуль: 1 — огляд та повторення C# Тип застосунку: консольний (.NET, Console App) Обсяг: 2 год аудиторних + СРС

    Мета роботи¶

    Отримати практичні навички проєктування класів за принципами ООП (інкапсуляція, успадкування, поліморфізм, абстракція), роботи з інтерфейсами та коректної обробки виключних ситуацій.

    Загальні завдання (обов'язкові для будь-якого варіанта)¶

    • Створити консольний проєкт (.NET 10, Console App) у Visual Studio / Rider / VS Code з назвою виду Lab2_<Прізвище>.
    • Спроєктувати ієрархію класів відповідно до варіанта: базовий (можливо, абстрактний) клас та щонайменше 2 похідні класи з перевизначенням (override) щонайменше одного методу.
    • Реалізувати інкапсуляцію: приватні поля, публічні властивості (у т.ч. з валідацією значення у set — наприклад, заборона від'ємної ціни чи порожнього імені), конструктори з перевантаженням (щонайменше 2 конструктори з різною кількістю параметрів).
    • Реалізувати щонайменше один інтерфейс (наприклад, IComparable<T>, власний інтерфейс на кшталт IDiscountable) і його реалізацію в кількох класах ієрархії.
    • Реалізувати колекцію об'єктів базового типу, що фактично зберігає похідні об'єкти (демонстрація поліморфізму) — обробка колекції через foreach з викликом віртуального методу. Виняток щодо вводу: колекцію дозволяється заповнити наперед у коді (масив-константа або кілька викликів конструкторів у Main), а не вводити всі об'єкти з клавіатури; при цьому в меню має бути пункт, що додає новий об'єкт до колекції через введення з клавіатури з валідацією (TryParse для числових полів). Для зберігання колекції можна використовувати як масив (тоді додавання — через Array.Resize), так і List<T> (тоді додавання — Add) — обидва варіанти рівноцінні.
    • Реалізувати власний клас винятку (успадкований від Exception, із трьома стандартними конструкторами) та обробку щонайменше 2 різних сценаріїв виключень (try/catch/finally, throw, власні та вбудовані винятки), включно з некоректними даними від користувача.
    • Реалізувати вивід результатів у зручному для читання вигляді. Табличний вивід з вирівнюванням стовпців не є обов'язковим, але вітається як ознака якісного оформлення.
    • Передбачити просте меню (цикл із вибором пункту), що дозволяє повторювати дії без перезапуску програми, аж до вибору пункту «Вихід».

    Приклади коду (для орієнтиру — не є готовим розв'язком варіанта)¶

    1. Базовий (абстрактний) клас, властивість з валідацією, перевантажені конструктори¶

    public abstract class Shape
{
    private string _name;

    public string Name
    {
        get => _name;
        set => _name = string.IsNullOrWhiteSpace(value)
            ? throw new ArgumentException("Назва фігури не може бути порожньою.")
            : value;
    }

    protected Shape(string name)
    {
        Name = name;
    }

    // Абстрактний метод — кожен похідний клас зобов'язаний його реалізувати
    public abstract double GetArea();

    // Віртуальний метод з реалізацією за замовчуванням, яку можна (не обов'язково) перевизначити
    public virtual void PrintInfo()
    {
        Console.WriteLine($"{Name}: площа = {GetArea():F2}");
    }
}

    2. Похідний клас, override, власний конструктор з перевантаженням¶

    public class Circle : Shape
{
    public double Radius { get; }

    public Circle(double radius) : base("Коло")
    {
        if (radius <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(radius), "Радіус має бути додатним.");
        }

        Radius = radius;
    }

    public override double GetArea() => Math.PI * Radius * Radius;

    public override void PrintInfo()
    {
        base.PrintInfo(); // виклик базової реалізації перед доповненням
        Console.WriteLine($"  Радіус: {Radius}");
    }
}

    3. Власний клас винятку (три стандартні конструктори)¶

    public class NegativeValueException : Exception
{
    public NegativeValueException() { }

    public NegativeValueException(string message) : base(message) { }

    public NegativeValueException(string message, Exception inner) : base(message, inner) { }
}

    4. Обробка кількох сценаріїв винятків (try/catch/finally)¶

    static void ProcessShape(Shape shape)
{
    try
    {
        double area = shape.GetArea();
        Console.WriteLine($"Площа: {area:F2}");
    }
    catch (NegativeValueException ex)
    {
        Console.WriteLine($"Помилка вхідних даних: {ex.Message}");
    }
    catch (Exception ex) // "запасний" обробник для непередбачених винятків
    {
        Console.WriteLine($"Непередбачена помилка: {ex.Message}");
    }
    finally
    {
        Console.WriteLine("Обробку фігури завершено.");
    }
}

    5. Поліморфна колекція, заповнена наперед у коді, з можливістю розширення¶

    List<Shape> shapes = new()
{
    new Circle(5),
    new Rectangle(4, 6)
};

// Викликається з пункту меню "Додати фігуру" — тут демонструється
// введення з клавіатури з валідацією через TryParse
static void AddCircle(List<Shape> shapes)
{
    double radius = ReadDouble("Радіус нового кола: ", min: 0.01);
    shapes.Add(new Circle(radius));
}

// Демонстрація поліморфізму: виклик virtual/override-методу через базовий тип
foreach (Shape shape in shapes)
{
    shape.PrintInfo();
}

    2. Реалізувати базовий клас (з властивостями з валідацією) та похідні класи з перевизначенням поведінки.
    3. Реалізувати інтерфейс(и) та їх використання поліморфно через колекцію.
    4. Реалізувати власний тип винятку та продемонструвати його виникнення й обробку поряд з обробкою хоча б одного вбудованого винятку.
    5. Написати консольне меню для демонстрації роботи всіх реалізованих сценаріїв, включно з пунктом додавання нового об'єкта до колекції.
    6. Протестувати граничні та помилкові випадки (див. «Граничний випадок для обробки» у своєму варіанті), зафіксувати їх у звіті.

    Варіанти завдань¶

    Кожен варіант описаний з конкретною структурою ієрархії класів, переліком обов'язкових полів/властивостей і методів та граничним випадком — щоб не залишалось відкритих запитань щодо обсягу роботи.

    Варіант 1. Геометричні фігури¶

    Ієрархія: абстрактний клас Shape (властивість Name) → похідні Circle (радіус), Rectangle (ширина, висота), Triangle (три сторони або основа й висота — на вибір студента).

    Обов'язкові операції: - абстрактний метод GetArea() — обчислення площі, реалізується в кожному похідному класі за власною формулою; - метод GetPerimeter() (може бути virtual з реалізацією-заглушкою в базовому класі або також abstract); - реалізація IComparable<Shape> за площею — щоб колекцію фігур можна було відсортувати List<T>.Sort(); - підрахунок сумарної площі всіх фігур колекції та виведення фігури з найбільшою площею.

    Граничний випадок для обробки: спроба створити фігуру з недодатним розміром сторони/радіуса — конструктор має викинути ArgumentOutOfRangeException (це не обов'язково саме власний клас винятку — власний клас винятку демонструється на іншому сценарії, наприклад при спробі обчислити периметр трикутника з некоректним співвідношенням сторін).

    Варіант 2. Транспортні засоби¶

    Ієрархія: базовий клас Vehicle (властивості Model, FuelTankVolume, FuelConsumptionPer100Km) → похідні Car, Motorcycle, Truck (у кожного — додаткова властивість, специфічна для типу: наприклад, вантажопідйомність у Truck).

    Обов'язкові операції: - метод CalculateFuelForDistance(double km) — розрахунок необхідної кількості пального на задану відстань (базова реалізація в Vehicle, Truck може перевизначити з коефіцієнтом на додаткову вагу вантажу); - метод CanTravelDistance(double km), що перевіряє, чи вистачить повного бака на задану відстань; - власний виняток InsufficientFuelException, що викидається, якщо запитується розрахунок для від'ємної відстані; - виведення списку всіх транспортних засобів колекції з підсумковою витратою пального на задану користувачем відстань (демонстрація поліморфного виклику).

    Граничний випадок для обробки: відстань, введена як 0 — витрата пального має коректно дорівнювати 0, а не викидати виняток (на відміну від від'ємної відстані, яка є помилкою).

    Варіант 3. Співробітники компанії¶

    Ієрархія: базовий клас Employee (FullName, BaseSalary) → похідні Manager (бонус за кількість підлеглих), Developer (надбавка за рівень: Junior/Middle/Senior), Intern (фіксована знижена ставка, без бонусів).

    Обов'язкові операції: - віртуальний метод CalculateSalary(), перевизначений у кожному похідному класі за власною формулою нарахування; - властивість BaseSalary з валідацією в set (заборона від'ємного або нульового значення — set викидає ArgumentException); - обчислення сумарного фонду заробітної плати по всій колекції співробітників; - пошук і виведення співробітника з найвищою розрахованою зарплатою (за результатом CalculateSalary(), а не за BaseSalary).

    Граничний випадок для обробки: спроба встановити BaseSalary через властивість у від'ємне значення (наприклад, після завантаження некоректних даних) — властивість має викинути виняток, а не мовчки зберегти некоректне значення.

    Варіант 4. Тварини в зоопарку¶

    Ієрархія: базовий (можливо абстрактний) клас Animal (Name, WeightKg) → похідні Predator (хижак — властивість PreyType), Herbivore (травоїдна — властивість PlantType), Bird (птах — властивість CanFly).

    Обов'язкові операції: - абстрактний або віртуальний метод MakeSound() та Feed() — обидва перевизначаються в кожному похідному класі з різним текстом/логікою; - інтерфейс IComparable<Animal> за вагою — для сортування колекції за зростанням/спаданням ваги; - обчислення сумарної добової норми корму по всій колекції (метод GetDailyFoodAmountKg(), залежний від типу тварини — наприклад, різний відсоток від ваги); - власний виняток InvalidWeightException при спробі створити тварину з недодатною вагою.

    Граничний випадок для обробки: колекція з однією твариною — сортування та пошук максимуму/мінімуму мають коректно відпрацювати і на колекції з одного елемента.

    Варіант 5. Побутова техніка¶

    Ієрархія: базовий клас ApplianceBase (Model, PowerWatts) → похідні WashingMachine (тривалість циклу в хвилинах), Refrigerator (працює безперервно 24 год/добу), TV (середня кількість годин роботи на день, що задає користувач).

    Обов'язкові операції: - віртуальний метод CalculateDailyEnergyConsumptionKWh() — розрахунок споживання електроенергії за добу, формула своя для кожного похідного класу (наприклад, для пральної машини — кількість запусків за день × тривалість циклу × потужність); - обчислення сумарного добового споживання всієї колекції техніки та приблизної вартості за тарифом (константа грн/кВт·год на початку програми); - пошук приладу з найбільшим споживанням; - власний виняток InvalidPowerException при спробі створити прилад з недодатною потужністю.

    Граничний випадок для обробки: телевізор із заданою кількістю годин роботи 0 (вимкнений увесь день) — споживання має коректно дорівнювати 0, а не викидати помилку.

    Варіант 6. Меню закладу харчування¶

    Ієрархія: базовий клас MenuItem (Name, Price) → похідні Beverage (об'єм у мл, признак «містить кофеїн»), MainCourse (калорійність, вага порції в грамах), Dessert (калорійність, признак «містить горіхи»).

    Обов'язкові операції: - віртуальний метод GetDescription() — форматований опис пункту меню, перевизначений у кожному похідному класі (з урахуванням специфічних полів); - обчислення сумарної вартості та сумарної калорійності обраного «замовлення» (підмножина пунктів меню, обрана користувачем через меню за номерами); - фільтрація меню за критерієм «без горіхів» (для варіанта з десертами) або «без кофеїну» (для напоїв) — вивести відфільтрований список; - власний виняток MenuItemNotFoundException при спробі додати до замовлення пункт за неіснуючим номером.

    Граничний випадок для обробки: замовлення без жодної обраної позиції — сумарна вартість і калорійність мають коректно дорівнювати 0, а не викидати помилку при діленні чи агрегуванні.

    Вимоги до звіту¶

    Звіт з практичної роботи оформлюється у вигляді документа (PDF/DOCX) та має містити:

    • тему, мету та номер варіанта завдання;
    • короткий опис реалізованого функціоналу;
    • посилання на репозиторій (GitHub/GitLab) з кодом проєкту та історією комітів;
    • знімки екрана (консоль) з демонстрацією роботи програми, у т.ч. обробки граничного випадку свого варіанта;
    • UML-діаграму (або її текстовий/Mermaid-опис) реалізованої ієрархії класів;
    • висновки (2–4 речення) щодо отриманих результатів та труднощів виконання.
